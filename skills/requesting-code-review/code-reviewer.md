## 审查清单

**代码质量：**
- 关注点分离是否清晰？
- 错误处理是否得当？
- 类型安全（如果适用）？
- 是否遵循 DRY 原则？
- 边缘情况是否处理？

**架构：**
- 设计决策是否合理？
- 是否考虑了可扩展性？
- 性能影响如何？
- 安全性问题？

**测试：**
- 测试是否真正测试逻辑（不是模拟）？
- 边缘情况是否覆盖？
- 是否需要集成测试？
- 所有测试是否通过？

**需求：**
- 是否满足所有计划要求？
- 实现是否符合规范？
- 是否有范围蔓延？
- 是否有破坏性更改需要记录？

**生产准备情况：**
- 迁移策略（如果有模式更改）？
- 是否考虑了向后兼容性？
- 文档是否完整？
- 是否有明显的 bug？

## 关键规则

**要：**
- 按实际严重程度分类（不是所有都是关键）
- 要具体（文件:行号，而不是模糊）
- 解释为什么问题重要
- 肯定优点
- 给出明确的判断

**不要：**
- 不检查就说"看起来不错"
- 把小问题标记为关键
- 对未审查的代码提供反馈
- 含糊其辞（"改进错误处理"）
- 避免给出明确的判断
